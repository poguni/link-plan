# 링크 플랜(Link Plan) 개발 보고서 (v1)

- 작성일: 2026-09-28
- 버전: v1

## 1. 개요

**링크 플랜(Link Plan)**은 할 일을 주간·월간·연간 목표에 연결해, 지금 하는 일이 큰 목표에 얼마나 기여하는지 진행률로 자동 보여 주는 개인용 할 일 관리 웹 앱입니다. 가입 후 관리자가 승인한 사용자만 쓸 수 있는 승인제 서비스이며, 클린·나이트·파스텔 3가지 테마와 보드 뷰·링크 뷰 2가지 화면(6가지 조합)을 지원합니다.

- **대상 사용자**: 연간 목표를 세우고 꾸준히 실천하려는 개인. 주 타깃은 자기계발형 직장인, 자격증·취업 준비생이고, 보조 타깃은 여러 프로젝트를 병행하는 프리랜서·1인 창작자입니다. 팀 협업·공유는 범위 밖입니다.
- **개발 기간**: 2026-09-26(PRD 작성) ~ 2026-09-28(배포 및 Phase 10 일부 P1 기능 구현). Claude Code와 함께 약 2~3일에 걸쳐 기획부터 배포까지 진행했습니다.
- **배포 주소**: `https://poguni.github.io/link-plan/` (GitHub Pages)

## 2. 목표 및 배경

### 문제 정의

- 할 일 목록과 목표가 따로 관리되어, 일을 끝내도 목표에 얼마나 가까워졌는지 알 수 없습니다.
- 연간 목표를 세워도 월간·주간·일일 실행 계획으로 내려오지 않아 중간에 흐지부지됩니다.
- 모든 할 일을 목표에 억지로 묶으면 입력 부담이 커져 앱을 떠나게 됩니다. "스마트폰 케이스 구입" 같은 잡무는 개별적으로 둘 수 있어야 합니다.

### 핵심 가치

| 가치 | 설명 |
|---|---|
| 연결 | 할 일 → 주간 계획 → 월간 계획 → 연간 목표의 4단계 구조로 실행과 목표를 잇습니다. |
| 자동 반영 | 할 일의 상태가 바뀌면 연결된 주간·월간·연간 목표의 진행률이 자동으로 다시 계산됩니다. |
| 선택적 연결 | 연결은 권장하되 강제하지 않습니다. 개별 할 일도 같은 화면과 같은 방식으로 관리합니다. |

### 성공 지표(제안값, 출시 전 가설)

| 지표 | 정의 | 목표 |
|---|---|---|
| 연결률 | 새로 만든 할 일 중 상위 계획에 1개 이상 연결된 비율 | 60% 이상 |
| 첫 주 계획 수립률 | 가입 후 7일 안에 주간 계획을 1개 이상 만든 사용자 비율 | 70% 이상 |
| 진행률 조회율 | 주 1회 이상 목표 진행률 화면을 본 활성 사용자 비율 | 70% 이상 |
| 4주 재방문율 | 가입 후 4주차에 다시 접속한 사용자 비율 | 40% 이상 |

## 3. 주요 기능

### 핵심(P0) 기능

- **할 일 CRUD**: 제목·수행일·메모 입력, 계획에 0개 이상 연결(연결 없으면 "개별 할 일").
- **계획 CRUD**: 연간·월간·주간 계획 생성·수정·삭제, 상위 계획 연결(주간→월간→연간만 허용).
- **3열 칸반 보드**: 시작 전/진행 중/완료, 드래그 앤 드롭(SortableJS) + 카드 Enter 키 메뉴(키보드 대안).
- **링크 뷰**: 연간→월간→주간→할 일 노드 그래프, SVG 연결선, 상태 트레이로 드래그 상태 변경.
- **진행률 자동 계산**: 서버의 `plan_progress` 뷰가 기준값이며, 하위 계획까지 집계합니다.
- **기간별 뷰**: 일일/주간/월간/연간 전환.
- **회원가입·로그인·관리자 승인**: 승인 전에는 앱을 쓸 수 없고, 관리자 승인 후 접근 가능.
- **관리자 페이지**: 사용자 목록, 승인/거절, 비밀번호 초기화, 사용자별 JSON 백업 저장.
- **반응형**: 1200px 이상 데스크톱, 1024~1199px, 600~1023px(가로 스크롤 스냅), 600px 미만(햄버거 드로어).
- **접근성**: 텍스트 대비 4.5:1 이상, 상태 표시에 색만 쓰지 않음, 키보드로 모든 조작 가능.

### 새로 추가된 기능(P1, Phase 10, 이번 세션)

- **P1-7 검색·필터**: 할 일 제목 검색 + 상태별(시작 전/진행 중/완료) + 계획별/개별 할 일만 보기 필터를 보드 뷰와 링크 뷰가 공통으로 씁니다.
- **P1-1 열 안 순서 변경**: 같은 상태 열 안에서 카드를 드래그해 우선순위 순서를 바꾸고 저장합니다.
- **P1-3 미완료 이월**: 주간 보드에서 이번 주 미완료 할 일을 한 번에 다음 주로 옮기는 버튼을 제공합니다.

> P1-1은 DB 스키마 변경(`tasks.sort_order` 컬럼)이 필요해 `supabase/05_sort_order.sql`을 별도로 준비했고, 아직 실제 Supabase 프로젝트에는 적용 전입니다(11절 참고).

## 4. 기술 스택 및 아키텍처

| 영역 | 선택 | 비고 |
|---|---|---|
| 프론트엔드 | Vanilla JS(ES 모듈), 빌드 도구 없음 | 번들러·프레임워크 없이 `<script type="module">`로 직접 로드 |
| 드래그 앤 드롭 | SortableJS(CDN) | 칸반 카드 이동·같은 열 재정렬, 링크 뷰 트레이 드롭 |
| 백엔드 | Supabase(Postgres, Auth, Data API, Edge Function) | 이 앱 전용 신규 프로젝트, 테이블 접두사 없음 |
| 인증·권한 | Supabase Auth + RLS | 모든 테이블에 `(select auth.uid()) = user_id and (select private.is_approved())` 형태 정책 |
| 관리자 기능 | Supabase Edge Function(`admin-api`, Deno) | `service_role` 키는 여기서만 사용, 프런트엔드·저장소에는 절대 두지 않음 |
| 배포 | GitHub Pages + GitHub Actions | `main` 푸시 시 자동 배포, `docs/`·`design/`·`supabase/`는 배포 대상 제외 |

### 코드 구조(핵심 JS 모듈)

| 파일 | 역할 |
|---|---|
| `js/app.js` | 진입점: 아이콘 로드 → 테마 복원 → 인증 게이트 |
| `js/state.js` | 메모리 상태 저장소(구독/알림 패턴), 모든 데이터 변경은 이 파일의 함수를 거침 |
| `js/api.js` | Supabase 어댑터(할 일·계획·연결·설정 CRUD), Postgres 오류를 사용자 문장으로 변환 |
| `js/filter.js` | (신규) 검색·필터 공유 상태, 보드·링크 뷰가 함께 구독 |
| `js/shell.js` | 앱 셸(상단바/사이드바/드로어), 테마·기간 전환, 검색·필터 패널, 계정 메뉴 |
| `js/board.js` | 보드 뷰 렌더링, 드래그, 상태 변경, 미완료 이월 |
| `js/link.js` | 링크 뷰 렌더링, 연결선, 상태 트레이 |
| `js/layout.js` | 링크 뷰 좌표 계산(DOM 없는 순수 함수) |
| `js/auth.js`, `js/authview.js` | 로그인·가입·승인 대기·비밀번호 변경 화면 |
| `js/admin.js` | 관리자 페이지(Edge Function 호출) |

### 아키텍처 특징

- **단일 DOM, CSS로 테마·뷰 분기**: `<html data-theme="…" data-view="…">` 속성만으로 6가지 화면을 전환합니다. 컴포넌트 CSS에는 색 코드를 직접 쓰지 않고 `tokens.css` 변수만 사용합니다.
- **구독 기반 상태 관리**: `state.js`가 단일 진실 공급원이며, 화면은 `subscribe()`로 변경을 받아 통째로 다시 그립니다(할 일 수백 개 규모에서는 충분히 빠름).
- **낙관적 업데이트**: 상태 변경(드래그, 순서 변경, 이월 등)은 화면을 먼저 바꾸고 서버 저장이 실패하면 되돌립니다.
- **진행률은 서버 기준**: 클라이언트 로컬 계산(`progress.js`)은 서버 값을 아직 못 불러왔을 때의 미리보기 용도로만 씁니다.

## 6. 주요 의사결정과 이유

- **빌드 도구 없는 Vanilla JS**: 프로젝트 규칙(CLAUDE.md)으로 처음부터 고정. 개인용 소규모 앱에 번들러·프레임워크 오버헤드가 불필요하다고 판단했습니다.
- **진행률은 서버 뷰(`plan_progress`) 기준**: 클라이언트마다 계산이 갈리는 것을 막고, `security_invoker`로 RLS(승인 조건 포함)를 그대로 따르게 했습니다.
- **`service_role` 키는 Edge Function에서만**: 관리자 기능(계정 삭제·비밀번호 초기화)은 반드시 서버에서 관리자 여부를 다시 검증한 뒤 실행합니다.
- **링크 뷰는 기간별로 필터링하지 않음**: 링크 뷰는 연결 구조 전체를 한눈에 보는 화면이라는 목적을 유지하기 위해 항상 전체 그래프를 보여 줍니다(기간 전환은 보드 뷰에만 적용).
- **좁은 화면(600px 미만)의 좌측 패널은 드로어**: 완전 아이콘 전용 레일은 계획 필터 기능을 없애 버리므로, 기능을 유지하는 햄버거 드로어를 선택했습니다(시안에 없는 구간이라 기능 우선으로 결정).
- **용어 "독립 할 일" → "개별 할 일"**: 사용자 피드백으로 어색한 표현을 수정하면서, "연결된 할 일"과 나란히 쓰이는 자리에서 의미가 겹치지 않는 "개별"을 선택했습니다(대안으로 "미연결"도 검토했으나 "연결 없음"과 겹쳐 제외).
- **P1-1 순서 값: 정수 대신 double precision(부동소수)**: 카드를 두 카드 사이로 끌어다 놓으면 (이전 값 + 다음 값) / 2를 계산해 저장하므로, 그때마다 같은 열의 다른 카드 순서를 다시 매길 필요가 없습니다(fractional indexing).
- **P1-3 이월은 계획 연결이 아니라 수행일 이동**: 계획 연결까지 옮기면 다음 주 주간 계획이 없을 때 처리가 애매해져, 수행일만 7일 뒤로 옮기고 계획 연결·진행률은 그대로 두는 단순한 방식을 택했습니다.
- **검색·필터 상태를 별도 모듈(`filter.js`)로 분리**: 기존에는 필터 상태가 `board.js` 안에만 있어 링크 뷰에서 쓸 수 없었습니다. 공유 모듈로 분리해 두 뷰가 같은 필터를 구독하도록 재구성했습니다.

## 7. 문제 해결 기록

| 문제 | 원인 | 해결 |
|---|---|---|
| 수정한 CSS/JS가 반영 안 됨 | 이전에 띄운 Python `http.server`가 같은 포트를 여전히 점유 | 실제 서버 헤더(`Server:` 값)로 프로세스 정체 확인 후 새 포트로 테스트, 이후 포트 정리 |
| 모바일(599px 이하) 레이아웃이 사이드바를 덮음 | `.main{grid-column:2}`가 트랙 1개짜리 그리드에서도 묵시적 2번째 열을 만듦 | 미디어 쿼리 안에서 `grid-column:1`로 명시 |
| 클린 테마 모바일에서 본문이 상단바를 가림 | 데스크톱 전용 `grid-row:1/-1` 규칙이 모바일 topbar 강제 모드에서도 유지됨 | 미디어 쿼리 안에서 `grid-row:2`로 재정의 |
| 드로어 배경이 드로어보다 위에 뜸 | `.shell{position:relative;z-index:1}`가 독립된 쌓임 맥락을 만들어 `body` 직속 배경의 z-index 비교가 어긋남 | 배경 요소를 `.shell` 내부에 추가해 같은 맥락에서 비교되게 함 |
| "내 계정" 버튼에 브라우저 기본 버튼 배경이 보임 | `background`/`border` 리셋 누락(전 테마·전 폭에서 존재하던 기존 버그) | 명시적으로 `background:transparent` 등 리셋 |
| 나이트·파스텔 계획 제목이 글자 단위로 줄바꿈 | `.goal-title`에 `overflow`/`text-overflow` 규칙이 클린 테마에만 있었음 | 공통 규칙으로 옮겨 3테마 모두 말줄임 처리 |
| 배포 후 `/admin.html` 등에서 404 | GitHub Pages의 Source가 "GitHub Actions"로 설정되지 않음 | 사용자가 대시보드에서 설정, Actions 탭에서 배포 성공 확인 |
| 관리자 페이지 버튼이 반응 없음(CORS) | Edge Function `ALLOWED_ORIGIN`에 경로(`/link-plan/`)까지 포함되어 브라우저가 보내는 Origin과 불일치 | 스킴+호스트만 남기도록 수정, curl 프리플라이트로 재확인 |
| 파스텔 테마 "완료" 칼럼 안에 정체불명의 동그라미 7개 | `css/view-board.css`(배너 요일 동그라미)와 `css/view-link.css`(링크 뷰 연결점)가 똑같이 `.dot` 클래스를 써서, 나중에 로드되는 파일이 이겨 배너 동그라미가 `position:absolute` 연결점 규칙을 물려받음 | 클래스명을 `.week-dot`으로 분리해 충돌 제거, Playwright로 `getComputedStyle`까지 확인 |

## 8. 보안/성능 고려사항

- **RLS 전면 적용**: `plans`·`tasks`·`task_plan_links`·`profiles`·`user_settings` 5개 테이블 모두 RLS를 켜고, `auth.uid()` + 승인 여부(`private.is_approved()`) 조건의 정책을 둡니다. `anon` 역할에는 기본 권한을 회수해 두었습니다.
- **`service_role` 키 격리**: 계정 삭제·비밀번호 초기화 같은 관리자 작업은 Edge Function `admin-api`에서만 처리하고, 호출자가 실제 관리자인지 서버에서 다시 확인합니다(RLS 우회 경로를 최소화).
- **저장소 비밀 값 스캔**: `service_role` 문자열, JWT 패턴, 비밀번호 리터럴, 개인 이메일을 저장소 전체에서 검색해 노출이 없음을 확인했습니다. `config.js`에는 anon(publishable) 키만 있습니다.
- **관리자 이메일 자리표시자화**: 공개 저장소이므로 `supabase/03_admin_bootstrap.sql`의 실제 관리자 이메일을 `ADMIN_EMAIL_HERE` 자리표시자로 교체했습니다.
- **성능**: 데이터가 바뀔 때마다 해당 영역을 통째로 다시 그리는 방식을 씁니다. 개인용 앱 규모(할 일 수백 개)에서는 이 방식이 충분히 빠르다고 판단해 가상 DOM 등 최적화 계층을 추가하지 않았습니다.
- **알려진 플랫폼 한계**: Supabase 무료 플랜에서는 "Leaked password protection"(HaveIBeenPwned 연동)을 켤 수 없습니다(Pro 플랜부터 제공). PRD 필수 항목이 아니라서 무료 플랜 운영 중에는 꺼진 채로 둡니다.

## 9. 테스트 및 검증

- **RLS 시나리오 테스트**: `supabase/04_rls_tests.sql`의 19개 시나리오(타인 데이터 접근 차단, 미승인 사용자 차단, 관리자 자기 자신 보호 등)를 SQL Editor에서 실행해 확인.
- **접근성**: axe-core(WCAG2A/AA)를 보드 뷰·링크 뷰·모바일 드로어·모달 열림 상태 4가지에서 실행해 위반 0건 확인. 텍스트 대비 4.5:1, 그래픽 3:1 기준도 재확인.
- **디자인 검수**: `DESIGN.md` 11절 체크리스트를 6가지 테마×뷰 조합에 대해 Playwright로 순회하며 새로고침 없는 전환, 콘솔 오류 없음, 하드코딩된 색 없음(정규식 스캔)을 확인.
- **레이아웃 순수 함수 검증**: `check-layout.mjs`로 `layout.js`의 좌표 계산 결과를 `design/DESIGN.md` 6-2 표와 대조(15개 중 13개 정확히 일치, 나머지 2개는 문서화된 설계 판단 차이).
- **배포 후 라이브 점검**: `gh` CLI 없이 GitHub REST API(curl)로 Actions 실행 결과를 확인하고, CORS 프리플라이트 요청으로 `Access-Control-Allow-Origin` 값이 실제 배포 주소와 정확히 일치하는지 확인.
- **Phase 10 스모크 테스트**: 새로 만든 `filter.js`·`board.js`·`shell.js`·`link.js`·`state.js`·`api.js`를 브라우저에서 동적 `import()`로 직접 로드해 문법·런타임 오류가 없는지 확인하고, `filter.js`의 검색/상태/계획 토글 로직을 직접 호출해 검증. `renderShell()`을 파스텔 테마로 강제 렌더링해 검색·필터 패널이 실제로 열리고 동작하는지 1440px·900px 폭에서 스크린샷으로 확인(가로 스크롤 없음 확인).

## 11. 알려진 한계

- **무료 플랜 제약**: 다운로드 가능한 자동 백업 없음(관리자 JSON 저장을 수동 백업으로 사용), 1주일 이상 미사용 시 프로젝트 일시정지 가능, leaked password protection 사용 불가.
- **PRD 열린 질문(미결정)**: 주간 계획이 두 달에 걸칠 때 자동 추천 규칙 필요 여부, 진행 중 가중치(P1-6) 기본 활성화 여부, 비밀번호 규칙에서 특수문자 허용 범위, 관리자 다중 지정 화면(P1-18) 필요 여부, 승인 취소·비밀번호 초기화 시 기존 세션 즉시 차단 여부.
- **Phase 10 배포 전 필수 작업**: `supabase/05_sort_order.sql`을 Supabase SQL Editor에서 먼저 실행해야 합니다. 이 컬럼이 없는 상태로 현재 코드를 배포하면 `js/api.js`의 할 일 조회 쿼리가 `sort_order` 컬럼을 요구해 전체 할 일 로딩이 실패합니다.
- **파스텔 테마 CSS 특이도 버그(미수정)**: `[data-theme="pastel"] .brand-tagline{display:flex}`가 `@media(max-width:1023px){.brand-tagline{display:none}}`보다 특이도가 높아, 900px 부근에서 태그라인 텍스트가 숨겨지지 않고 3줄로 줄바꿈됩니다(페이지 가로 스크롤은 발생하지 않음).
- **통짜 재렌더링 방식**: 할 일이 매우 많아지면(수천 개 이상) 매번 전체를 다시 그리는 현재 방식이 느려질 수 있습니다. P1-12(링크 뷰 대량 데이터 대응)가 이를 다루도록 남겨져 있습니다.
